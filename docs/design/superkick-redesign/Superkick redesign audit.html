SUPERKICK · UX/UI AUDIT · MAY 2026

From internal tool to calm operations workspace.

Superkick a tout pour devenir un mission control élégant et lisible. Aujourd'hui l'app fait "internal tool dense" — beaucoup de DM Mono UPPERCASE, beaucoup de sections empilées, deux entrées de launcher concurrentes. Cet audit propose une direction visuelle, 6 problèmes UX prioritaires, 4 principes de redesign, et 6 tickets shippables — chacun avec scope, non-goals, et critères d'acceptation.

Direction   Linear · Multica · Claude Surfaces   Shell · Inbox · Issues · Issue Detail · Launch Task · Run Detail Constraint   No IA change · Ticket-first stays

On garde la palette Graphite Operations Atelier (tokens existants). Ce qui change : on lève le pied sur le mono uppercase, on laisse respirer la grille, on traite chaque surface comme une lecture — pas comme un panneau d'admin.

02Problèmes UX actuels

Observations sur le code actuel (ui/src/components/*) et la direction visual-design.md. Listés par ordre d'impact perçu sur l'usage quotidien.

P-01

Le chrome parle en télégramme

Headers, sidebars, banners, statuts : tout est font-data uppercase tracking-[.18em]. C'est l'esthétique "Multica trader UI", pas Linear. Résultat : l'app a l'air d'un outil internal-only et la lecture est fatigante en daily use. Le mono doit rester réservé aux IDs, durées et états techniques.

P-02

Deux launchers concurrents pour la même action

Sur Issue Detail, le panel droit contient LaunchTaskLauncher (recette Plan→Implement→Review) et une Disclosure "Advanced — launch a single isolated run" qui ouvre LaunchDialog. Deux flows pour lancer un truc. L'utilisateur ne sait pas lequel choisir, et le "single run" est un legacy escape hatch qui pollue la surface principale.

P-03

L'Inbox n'a pas de hiérarchie d'urgence

Quatre sections empilées (NeedsHuman · RunningNow · ReadyToLaunch · RecentlyDone), même poids visuel pour chacune, même header style. "Needs you" devrait dominer la page, pas être un titre parmi quatre. Pas de verbe d'action explicite sur les rows ("Answer", "Approve", "Take over").

P-04

Issue Detail surcharge la zone principale

Top-down on a : NeedsHuman banner · Issue title · Launch Task feed · Description · Children · Activity timeline. C'est 5 sections de hauteur libre dans la colonne principale. Le Launch Task feed — qui est l'objet produit principal — est mélangé à la description Linear et à un timeline de commentaires. Aucune surface n'est mise en avant.

P-05

Run Detail est une liste de tiroirs

RunDetailView empile 5 EvidenceSection collapsibles : ledger, step timeline, sessions, reviews, terminal. C'est exhaustif mais ce n'est pas une histoire. L'utilisateur veut savoir "où on en est, qu'est-ce qui bloque", pas naviguer une table des matières.

P-06

Trois bars horizontales mangent le viewport

ShellHeader (h-12) + SessionWatchRail (h-8 à h-10) + RunDock en bas = ~120px de chrome avant même de voir le contenu. Sur un MacBook 13", c'est cher payé.

03Principes de redesign

Quatre règles qui décident des arbitrages dans chaque ticket.

1 · Le ticket est l'objet, pas l'évidence.

L'écran principal d'une issue, c'est le Launch Task et son état. Description, comments, children s'effacent au-dessous. Le launcher est central, jamais dans une aside cramped à 20rem.

2 · Une action attendue par écran.

Inbox row, run card, issue header → toujours une seule "next action" lisible : Answer · Approve · Resume · Take over. Pas trois boutons équivalents.

3 · Le mono est une exception.

DM Mono pour : IDs (SUP-217), durées (2m 14s), états techniques (RUNNING), valeurs numériques. Tout le reste en DM Sans. Plus de headers UPPERCASE par défaut.

4 · Le terminal est un escape hatch.

Visible, accessible, mais visuellement calme. Le takeover est une promesse de pouvoir, pas une invitation par défaut. Aucune surface ne doit ressembler à un terminal.

046 tickets shippables

Ordonnés par dépendance : on commence par les fondations (chrome typo + density), puis on consolide les surfaces l'une après l'autre. Chacun est livrable en une à deux semaines, isolé, et n'introduit aucune feature produit nouvelle.

SUP-217FoundationCross-cutting

Tone down the chrome: typo, casing & sidebar harmonization

3–4 days 1 frontend
Objectif
Donner à Superkick une voix calme et lisible. Le chrome (sidebar, headers, section titles, banners) parle en DM Sans sentence case. DM Mono survit seulement pour la data.
Scope
  • Audit + remove de font-data uppercase tracking-* sur tous les headers de chrome (Sidebar brand, ShellHeader, SectionTitle, InboxSection header, RunDetailHeader, IssueDetailHeader, panel titles).
  • Helper component <SectionTitle> unifié : DM Sans 13/14px, weight 500, sentence case, count en mono ash.
  • ShellHeader passe de h-12 à h-11. SessionWatchRail devient optionnel et collapse quand 0 watched.
  • Sidebar : brand "Superkick" en DM Sans 13px medium au lieu du tracking-wider uppercase.
Non-goals
  • Ne pas toucher aux IDs (SUP-217) ni aux durées ni aux états techniques (RUNNING).
  • Pas de changement de palette ni de tokens.
  • Pas de refactor d'IA, juste cosmétique.
Critères d'acceptation
  • Grep uppercase tracking- retourne < 10 occurrences (vs ~50 aujourd'hui), toutes sur des labels techniques justifiés.
  • Aucun header de section en mono uppercase.
  • visual-design.md mis à jour avec la nouvelle règle "mono = data only".
  • Screenshots avant/après sur Inbox + Issue Detail + Run Detail joints à la PR.

SUP-218InboxHigh impact

Inbox: triage queue, not metrics board

5–6 days 1 frontend
Objectif
L'Inbox doit répondre à une seule question en 2 secondes : "qu'est-ce qui attend moi maintenant ?". On la transforme en file d'attente d'interruptions, avec un verbe d'action par ligne.
Scope
  • Needs you devient une zone dominante en haut (titre h2 sans uppercase, lignes oxide-bordered, action verb visible).
  • Chaque NeedsHumanRow expose un bouton primary explicite : Answer · Approve · Resume · Take over. Le verbe est calculé depuis reasonKind.
  • Running · Ready · Done deviennent des sections secondaires unifiées (typo plus discrète, count à droite).
  • Largeur passe de max-w-3xl à max-w-4xl pour respirer la deuxième ligne (reason / branch).
  • Empty state quand 0 needs-human : "All clear" + count des running. C'est le bon état par défaut.
Non-goals
  • Pas de nouveau bucket. On garde NeedsHuman / RunningNow / ReadyToLaunch / RecentlyDone.
  • Pas de métriques agrégées (succès / failure rate). L'Inbox n'est pas un dashboard.
  • Pas de filtre ni de search dans cette pass.
Critères d'acceptation
  • Chaque NeedsHuman row a un CTA visible et keyboard-accessible.
  • Quand 0 needs-human, l'écran montre clairement "all clear" et le focus est sur Running.
  • Sidebar nav Inbox badge réutilise needsHumanCount avec accent oxide quand > 0.
  • a11y : aria-label sur chaque row inclut le verbe ("Answer SUP-217").

SUP-219Launch TaskHigh impact

Consolidate the Launch Task launcher: one path, no legacy dialog

4–5 days 1 frontend, light backend touch
Objectif
Supprimer la dualité Launch Task vs Advanced single run. Le launcher devient unique, central sur Issue Detail, et lisible.
Scope
  • Retirer le Disclosure "Advanced — launch a single isolated run" du IssueLauncherPanel. La LaunchDialog reste accessible via menu ·· › du header Issue ("Run without recipe"), mais n'est plus dans la surface principale.
  • Le launcher (Plan → Implement → Review) sort de l'aside et devient une zone hero pleine largeur sur Issue Detail (voir T5).
  • Refactor visuel de LaunchTaskLauncher : 3 cards horizontales (une par step) + un footer avec Launch task en primary mineral. Plus de mono uppercase sur "Plan → Implement → Review".
  • Persister le dernier agent choisi par step au niveau du repo (localStorage suffit pour V1).
Non-goals
  • Ne pas casser LaunchDialog : il reste utilisable pour les power users.
  • Pas de nouveau type de recipe.
  • Pas de configuration globale d'agents par défaut (reste sur superkick.yaml).
Critères d'acceptation
  • Sur Issue Detail sans active task, on voit un seul bouton primary Launch task.
  • LaunchDialog n'est plus rendu par IssueLauncherPanel.
  • Le choix d'agent par step est restauré entre sessions.
  • Aucun changement d'API. useCreateRun est conservé pour le menu power-user.

SUP-220Launch TaskEvidence

Launch Task feed: evidence cards, not bullet list

4–5 days 1 frontend
Objectif
Quand une task tourne, l'utilisateur doit lire l'avancement comme une histoire : "Plan ok, Implement en cours (ran tests, edited 4 files), Review pending". Pas comme une checklist.
Scope
  • Refactor LaunchTaskFeed en 3 step cards verticales : status ring + step name + agent + 2-3 evidence lignes (tool calls collapsed).
  • Le step en cours est mis en avant : pulse cyan/neon sur le ring, surface bg-slate légèrement plus claire.
  • Evidence : "Edited 4 files", "Ran tests · passed", "Opened PR #82" — chacune cliquable pour ouvrir le détail. Réutiliser le payload protocol events déjà parsé.
  • CTA "View linked run →" remplacé par un bouton inline plus discret "Inspect run" en bas de la step active.
  • Bouton Cancel et Retry dans le header de la card, plus dans une dropdown séparée.
Non-goals
  • Ne pas recréer le run ledger ici. Garder le ledger dans Run Detail.
  • Pas de stream live des logs dans la card (reste protocole-first, on parse).
  • Pas de chat embarqué dans le feed (le ChatDrawer reste séparé).
Critères d'acceptation
  • Sur une task running, l'utilisateur identifie le step en cours en < 1s.
  • L'evidence (tool calls résumés) est visible sans drilling.
  • Cancel/Retry sont au max à 1 clic depuis la feed card.
  • Sur une task needs_human, la card du step active est bordée gold avec un Banner inline "Reviewer is waiting on you".

Run Detail: supervision view, not a folder of accordions

6–7 days 1 frontend
Objectif
Quand on ouvre un run, on doit lire en une scan : où on en est, qu'est-ce qui bloque, où agir. Pas naviguer 5 sections collapsibles.
Scope
  • Header simplifié : titre issue + state pill + actions primary contextuelle (Approve / Cancel / Take over).

  • Le step actif est identifiable en < 1s.
  • L'action humaine attendue (si elle existe) est au-dessus du fold avec un CTA primary.

06Light mode

Direction proposée : un light mode paper-first (pas un dark inversé). Surfaces chaudes neutres, accents légèrement désaturés pour rester lisibles sur fond clair. Mêmes tokens sémantiques, même hiérarchie d’élévation. Toggle haut-droite pour prévisualiser tout ce document en clair.

Surfaces (light)

Paper stack

Void chaud → Carbon → Graphite (white card) → Slate.

Accents (light)

Desaturated

Légère baisse de chroma pour la lisibilité sur fond clair.

Règles

Pas un dark inversé

  • · Le fond n’est jamais #fff au root. --void = papier légèrement chaud (#f6f5f1).
  • · Les cards passent en blanc pur pour émerger du papier (l’inverse du dark : graphite au-dessus du void).
  • · Les bordures portent plus de poids visuel — elles remplacent les ombres internes du dark.
  • · Les accents dim (mineral-dim, oxide-dim…) restent en rgba ; mais on baisse l’opacité à ~10% au lieu de 12%.
  • · Le pulse neon-green devient mineral en light — le néon flashe trop sur papier.
SUP-223FoundationTheme

Light mode: paper-first companion theme

4–5 days1 frontend
Objectif
Donner à Superkick un light mode complet, lisible en journée, sans renier l’identité calme du dark. Mêmes tokens, même hiérarchie, palette déclinée papier.
Scope
  • Ajouter un set de tokens [data-theme="light"] dans ui/src/index.css (surfaces + texte + accents desaturés).
  • Toggle dans le menu Settings + raccourci ⌘⇧L. Préférence persistée dans localStorage, default = prefers-color-scheme.
  • Audit shadcn variables (--background, --card, --primary…) : redéclarer sous [data-theme="light"].
  • Sweep des composants qui hardcodent bg-carbon / bg-graphite sans token (re-utiliser celui-ci doit être suffisant). Lint rule pour interdire bg-zinc-* / #hex en dur.
  • Re-tester les 6 surfaces principales (Inbox, Issues, Issue Detail, Launch Task feed, Run Detail, Settings) en light + screenshots regression.
Non-goals
  • Pas un dark inversé : ne pas mapper #0b0c0e → #fff.
  • Pas de variation d’accent par theme (semantics restent : mineral=ok, oxide=fail…).
  • Pas de “auto” suivi du système en temps réel dans cette pass — lu une fois au boot.
Critères d’acceptation
  • Toggle visible dans Settings + raccourci clavier.
  • Aucune régression contrast WCAG AA sur les 6 surfaces principales.
  • Grep #[0-9a-f]{3,8} dans components/ retourne 0 résultats hors index.css.
  • visual-design.md mis à jour avec la règle “light mode = paper-first, not inverted”.
